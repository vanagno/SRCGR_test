# Greece Finite-Fault Slip Model Geobrowser (SRCGR)

A FAIR-aligned, community-compiled, interactive database of published coseismic and
postseismic finite-fault slip models for earthquakes in Greece and the surrounding
region. Companion resource to Vavlas & Bonatis, *(in prep.)*.

The site is a single static page. `build.py` validates every record in
`data/models/`, groups the records into earthquakes, and inlines them into
`template.html` to produce `dist/index.html` (plus machine-readable copies of the
data). GitHub Actions builds the site and publishes it to GitHub Pages on every
push to `main`.

What the page offers:

- A map with one star per earthquake (sized by magnitude) at its hypocenter, a
  basemap switcher (satellite by default), a distance-measuring tool and a home
  control.
- An earthquake list with one row per earthquake, ordered by origin time. A row
  expands to list the earthquake's slip models. Search, magnitude, event-year and
  publication-year sliders, and faulting-style and data-type filters narrow the
  list and the map (see
  [Earthquakes and models on the page](#earthquakes-and-models-on-the-page)).
- For the selected earthquake: a selector of all its published slip models. For
  the selected model: the source parameters, the fault geometry and slip
  projected on the map, a slip overview with a full-screen viewer, data-quality
  notes, a citation (plain text and BibTeX), and downloads (record JSON, patch CSV).
- An optional live overlay of recent seismicity (EMSC, with USGS as fallback).
  It is off by default.
- A permalink for every model (see [Permalinks](#permalinks)).

Many records were digitized from figures or tables in the source papers, not taken
from author-supplied files. Every record says where its numbers come from
(`provenance.data_origin`), and the page shows this next to the model.

## Repository layout

| Path | What it is |
| --- | --- |
| `schema.json` | JSON Schema (draft 2020-12) that every record must follow. Key fields have a `description`. The sections below explain the rest. |
| `data/models/*.json` | One file per slip model. These files are the source data, and the build never rewrites them. |
| `build.py` | Validates the records, matches them to earthquakes and writes `dist/`. |
| `template.html` | The single-page browser. The build inlines the data into it. |
| `event_registry.json` | Generated by the build and committed. It holds the persistent earthquake keys and the file-to-earthquake assignments. |
| `event_overrides.json` | Optional and edited by hand. It holds manual earthquake-matching decisions (see [Automatic event matching](#automatic-event-matching)). |
| `tests/` | `pytest` tests for `build.py`. |
| `requirements.txt`, `requirements-dev.txt` | Build dependencies, and those plus the test dependencies. |
| `CONTRIBUTING.md` | Short checklist for contributors. |
| `.github/workflows/deploy.yml` | CI: validates pull requests, and builds and deploys `main` to GitHub Pages. |
| `dist/` | Build output (not committed). |
| `event_review.json` | Written by the build when event matching needs a decision, or as non-blocking notes when published models have no origin time (not committed). |

## Adding a slip model

1. **Name the file** `<EventCamelCase><Year>_<Author>_<PubYear>.json`, for example
   `Samos2020_Aktug_2021.json`, `CretanBasin2012_Kiratzi_2013.json` or
   `Lemnos2013_KiratziSvigkas_2013.json`. The file name without `.json` becomes the
   record's permanent ID on the site: it is used in permalinks, in download names
   and in `data/<id>.json`. A name that does not follow the pattern still builds,
   and the build lists it in one `NOTE` line. `models.json` (in any letter case) is
   an error, because that name is reserved for `data/models.json`. Avoid renaming a
   published file, because its permalink changes. If you do rename one, see
   [Automatic event matching](#automatic-event-matching). If one publication gives
   several alternative models, put each in its own file with a distinguishing file
   name. Such files may share the same `model_id`.
2. **Start from an existing record** of a similar kind in `data/models/`, then fill in
   the values for the new model. Follow the field definitions in `schema.json`.
   - Set `"schema_version": "1.1.0"`. Records written for 1.0.0 stay valid.
   - Required fields: `schema_version`, `event`, `reference` and
     `fault_segments`.
   - `model_id` and `event.event_id` are optional and informational only. The build
     never uses them to match records, so you do not need to coordinate IDs with
     other contributors. If you give a `model_id`, it follows
     `<event>_<firstauthor>_<year>` in lower case, for example
     `samos2020_aktug_2021`. The pattern is `^[a-z0-9]+_[a-z]+_[0-9]{4}$`.
   - If you leave out `model_id` or `event.event_id` (an empty `event_id` counts as
     left out), the build fills it in on the published copies: the page, its record
     downloads and `dist/data/`. `event.event_id` becomes the earthquake key
     (see [Automatic event matching](#automatic-event-matching)). `model_id` becomes
     `auto<hash>_<surname>_<year>`: 16 hexadecimal digits derived from the file
     name, the first author's surname in lower case and `reference.year`. For
     example, `Samos2020_Aktug_2021.json` gets `autod395802edda05026_aktug_2021`.
     Your file is not changed.
   - `event.origin_time` is an ISO 8601 UTC time such as `2020-10-30T11:51:26Z`.
     Use `null` only when the time is unknown, for example for historical events.
   - `reference.authors` lists every author, never `"et al."`. `reference.doi` is the
     bare DOI (`10.xxxx/...`, without `https://doi.org/`). `reference.url` must start
     with `http://` or `https://`.
3. **Work in progress:** add `"status": "draft"` at the root. The build validates
   drafts and only prints their problems. Drafts are never published, never
   matched to earthquakes and never added to the registry. The data-quality checks
   run on a draft only once it passes the schema. Until then the build prints
   `consistency checks skipped (record is not schema-valid)`. A draft that is not
   valid JSON still stops the build, because the build cannot read its `status`.
   When the record is complete, remove `status` or set it to `"published"`.
4. **Check locally** (see [Running locally](#running-locally)) or open a pull
   request. CI runs the same checks, and nothing is deployed until the change is
   on `main`.
5. **Commit `event_registry.json`** together with your change if the build changed
   it. Adding, renaming or editing a record can change it.

Only a few objects accept extra keys: `reference`, `inversion`, `summary_metrics`,
`model_variant` and `provenance`. Use them for things like digitization notes. Every
other object is strict, so a misspelled key there is reported as an error.

### Provenance

`provenance` records where the numbers come from:

| Field | Meaning |
| --- | --- |
| `data_origin` | `author_supplied` (numerical values from the authors, e.g. a supplementary file), `srcmod` (taken from SRCMOD), `digitized_figure` (digitized from a published figure), `digitized_table` (transcribed from a published table), `derived` (computed from other published values), `other` (explain in `inversion.notes`). |
| `source_figure` | The figure or table used, e.g. `"Figure 5"`, `"Figure 3b"`, `"Table 2"`. |
| `verified_by` | Who checked the digitized or transcribed values against the publication. |
| `uncertainty_notes` | Digitization resolution, colour-scale quantization and similar. |
| `license` | Licence of the record. If this is missing, the page shows "not specified", and the build lists the record in one `NOTE` line with all other published records that have no licence. |
| `source_file_url` | Link to the original supplementary data, or `null`. |
| `compiled_by`, `date_added` | Who added the record, and when (`YYYY-MM-DD`). |

### Fault geometry, reference point and patches

Each fault segment is a rectangular plane (`strike_deg`, `dip_deg`, `length_km`,
`width_km`, `top_depth_km`). An optional `name` labels the segment in the browser.

**Fault-plane frame.** Patches and the reference point use the same frame:

- `along_strike_km` is measured from the start of the segment in the strike direction.
- `down_dip_km` is measured from the top edge, along the dipping plane.
- Strike and dip follow the Aki-Richards right-hand convention: looking along strike,
  the fault dips to the right, so the down-dip azimuth is strike + 90°.
- A patch's `along_strike_km` and `down_dip_km` are the coordinates of its centre.
  Its `depth_km` is expected to equal `top_depth_km + down_dip_km · sin(dip)`. Patch
  `latitude` and `longitude` may be `null`. The browser then derives the patch
  positions from the geometry.

**`reference_point`** gives the geographic anchor of the segment (`latitude`,
`longitude`). The anchor is placed on the plane as follows:

| Given | Meaning on the fault plane |
| --- | --- |
| `along_strike_km` and `down_dip_km` | The exact plane coordinates of the point. Give both or neither (the schema rejects only one). They override `position` for the placement. If they contradict a `top_left`, `top_center` or `center` position, the build warns (see [Validation](#validation)). |
| `position: "top_center"` | Midpoint of the top edge. |
| `position: "top_left"` | The patch-coordinate origin: along strike 0 on the top edge. |
| `position: "center"` | Centre of the plane. |
| `position: "hypocenter"` | The point is the event hypocenter (lat/lon = epicenter). Also give its plane coordinates if the paper states them. Otherwise the browser treats the point as the plane centre and labels the placement *approximate*. |
| `position: "unknown"`, or nothing | Not stated. The browser assumes `top_center` and labels the placement *assumed*. |

For points below the top edge, `latitude` and `longitude` are the point's surface
projection. Do not guess `position`: if the paper does not say which point it is,
leave it out.

**Map star.** The map has one star per earthquake, shared by all of its models. The
build gives every model of an earthquake the same location (the browser-only field
`_browser_event_location`): the `event.hypocenter` of the earthquake's first file in
sorted file-name order or, if that hypocenter has no coordinates, the hypocenter of
the first file that has them. The star is placed there. Only when no model of the
earthquake has hypocenter coordinates does the page use other coordinates, from the
first of its models (by publication year, then citation, then file name) that has
any: a reference point with `position: "hypocenter"`, else one with
`position: "center"`, else the first reference point that has coordinates, else the
first patch with `latitude` and `longitude`. An earthquake whose models have no
coordinates at all has no star, but it stays in the list. The star's size follows the magnitude of the model the
earthquake is named after (see
[Earthquakes and models on the page](#earthquakes-and-models-on-the-page)), and its
colour the faulting style.

### Data types (`inversion.data_types`)

| Value | Data |
| --- | --- |
| `teleseismic` | Teleseismic body or surface waveforms |
| `strong_motion` | Near-field strong-motion (accelerometer) records |
| `regional_waveforms` | Regional broadband waveforms, including empirical-Green-function and source-time-function inversions of regional records |
| `GNSS` | GNSS displacements (static offsets or high-rate) |
| `GPS_static` | Legacy alias of static GNSS offsets. Prefer `GNSS`. |
| `InSAR` | InSAR line-of-sight displacements |
| `field_mapping` | Field observations of surface rupture or offsets |
| `tsunami` | Tsunami waveforms (tide gauges, offshore pressure sensors) |
| `coastal_uplift` | Coastal uplift or subsidence markers, such as raised shorelines |
| `leveling` | Levelling (vertical geodetic) lines |
| `macroseismic` | Macroseismic intensity observations |
| `other` | Anything else. Describe it in `inversion.notes`. |

## Automatic event matching

Contributors do not need to agree on event IDs. `build.py` decides which records
describe the same earthquake from the origin time, epicenter and magnitude.
`event.event_id` and `model_id` are not used for this, and both may be left out.

A file that already has an earthquake in `event_registry.json` keeps it (see
below). Every other file is processed in sorted file-name order and compared with
every earthquake known so far: those in the registry and those created earlier in
the same run. An earthquake is represented by the current record of its first file
in sorted file-name order. The data stored in the registry are used only for
earthquakes that no present file belongs to.

The rules never guess a merge. Only near-identical origins match. Anything close
but not identical is a possible match, which needs a decision. The rows are checked
in order:

| Comparison | Result |
| --- | --- |
| Either side has no origin time | different |
| Origin times more than 300 s apart, or \|ΔM\| > 1.5 | different |
| Both have coordinates, more than 50 km apart | different |
| Both have coordinates: ≤ 5 s, ≤ 20 km and \|ΔM\| ≤ 0.5 | match |
| Both have coordinates, otherwise | possible match |
| Coordinates missing on either side: ≤ 1 s and \|ΔM\| ≤ 0.4 | match |
| Coordinates missing on either side, otherwise | possible match |

Coordinates are the latitude and longitude of `event.hypocenter`, and distances are
great-circle distances between them. The limits are inclusive. Magnitudes are
compared as written, so 6.4 and 6.0 differ by exactly 0.4.

- If there is exactly one match and no other match or possible match, the file
  joins that earthquake.
- If nothing matches, the file starts a new earthquake.
- A match or possible match with an earthquake kept `"separate"` (see below) always
  needs a decision. It is listed under `possible_matches` and is never merged
  silently.
- In any other case, the build stops without generating the site or changing the
  registry. It lists the ambiguous files and writes `event_review.json` with a
  `review` list (`file`, `matches` and `possible_matches` for each). Resolve this
  with `event_overrides.json`.
- A record without `origin_time` is never merged automatically. It becomes its own
  earthquake (shown as a data-quality note) unless an override assigns it. An
  `origin_time` that is present but malformed is an error.

**Records without an origin time** do not stop the build. When the build succeeds
and published records have no `origin_time`, it writes `event_review.json` with
`"status": "non_blocking_metadata_warnings"` and one entry under `warnings` per
record (`file`, `reason`, `event_key`, `action`). At the end of its output it
prints `WARNING: N model(s) lack a verified UTC origin time:` and lists the files.
Records with an entry in `event_overrides.json` have been decided by a maintainer
and are not listed. To clear a note, add a sourced UTC `origin_time` to the record,
or map the file to a verified earthquake key in `event_overrides.json`. When no
record needs a note, a successful build deletes `event_review.json`.

**Renamed files.** A file with no committed assignment, such as a renamed file, can
take over an earthquake that no present file belongs to any more. It does so when its
data equal the data stored for that earthquake: the same origin time, magnitude and
name, plus the same coordinates for a dated record. So a renamed file whose content
is unchanged keeps its earthquake key. This also works for undated records and for
records without coordinates. If the data change in the same commit, before a build
has recorded the new name in the registry, the file is matched normally.

**`event_registry.json`** keeps earthquake keys stable. A file that is already
assigned stays with its earthquake on later builds, and a key never changes, even
when the data it was made from change. On every build, each earthquake's
`origin_time_utc`, `latitude`, `longitude`, `magnitude` and `name` are refreshed from
its first file (in sorted file-name order). The registry keeps that file's own
coordinates, even when they are missing. The name the page shows and the position
of the star follow their own rules (see
[Earthquakes and models on the page](#earthquakes-and-models-on-the-page), and
*Map star* under [Fault geometry](#fault-geometry-reference-point-and-patches)).
When a committed earthquake changes, the build prints
`NOTE: registry event '<key>' updated from <file>: ...` with the old and new values.
If the edited earthquake now matches or possibly matches another one, the note adds
`it now resembles [...]`. If they are the same earthquake, map the files to one key
in `event_overrides.json`. If another file of a shared earthquake is now clearly
different from the earthquake's first file, it stays, and the build prints
`NOTE: <file>: kept registry event '<key>' although the record no longer matches
<first file> (...)`.

Keys look like `2020-10-30_30-october-2020-samos-aegean-sea`, or `undated_<name>`
when there is no origin time. The key is made when the earthquake is first seen. A
key that starts with `undated_` stays when an origin time is added to the record
later, for example `undated_7-september-1999-athens-earthquake`. Keys are not shown
on the page or used in permalinks. They appear in published records only as a
filled-in `event.event_id`. The registry contains only earthquakes that have at
least one file. Its output is deterministic, so rebuilding unchanged data produces
no diff. Commit it whenever the build changes it. CI warns when a pushed or proposed
change leaves it out of date.

**`event_overrides.json`** (optional, in the repository root) maps a model file name
to an earthquake key, or to `"separate"`:

```json
{
  "Samos2020_NewAuthor_2023.json": "2020-10-30_30-october-2020-samos-aegean-sea",
  "Kos2017_OtherAuthor_2020.json": "separate"
}
```

- A key must already exist in `event_registry.json` or come from `event_review.json`.
  An unknown key is an error.
- `"separate"` gives the file an earthquake that never absorbs other files
  automatically. A later file that matches or possibly matches it goes to review.
- If the file shares a committed earthquake with other files, it leaves that
  earthquake for one of its own only if another file keeps the earthquake through
  its committed assignment, without an override. The shared earthquake then stays
  open for new models. Otherwise the file keeps the key, and that earthquake is
  kept separate.
- An entry for a file that does not exist, or for a draft, is ignored, and the build
  prints a note.
- Overrides take precedence over the registry. Contributor files are never edited
  to resolve matching.

## Validation

**Errors** stop the build:

- invalid JSON, reported with file, line, column and context. `NaN`, `Infinity` and
  numbers too large to be finite (such as `1e999` or a 400-digit integer) are
  rejected as invalid JSON too;
- schema violations, including format checks: `date-time` for `event.origin_time`,
  `date` for `provenance.date_added`, and `uri` for `reference.url` and
  `provenance.source_file_url`;
- unknown keys in strict objects;
- a key named `__proto__` anywhere in a record;
- text or keys that are not valid Unicode, i.e. that contain unpaired surrogates
  such as `"\ud800"`;
- template placeholders left in a published record: any text containing
  `REPLACE_WITH`, URLs on `example.org`, `example.com` or `example.net`, and author
  entries like `et al.`;
- a record file named `models.json` (in any letter case), because that name is
  reserved for `data/models.json`;
- event matching that needs review (see above).

Each error in a record's content names its JSON path, for example
`at reference/doi: 'REPLACE_WITH_DOI' does not match ...`. Draft records are
validated too, but their problems are only printed. A file that is not valid JSON
stops the build even when it is a draft. A file name that does not follow
`<EventCamelCase><Year>_<Author>_<PubYear>.json` is not an error: the build lists
such names in one `NOTE` line.

When the build fails, `dist/` and `event_registry.json` are left unchanged. Every
output is rendered in memory and staged before any file is replaced. The only file
written on failure is `event_review.json`, when event matching needs review.

**Warnings** are consistency checks. They never stop the build. They are printed
per file and shown on the page under *Data-quality notes* for the model:

- the patch count is not `n_along_strike × n_down_dip`, or patch positions are duplicated;
- `n_along_strike × patch_length_km` differs from `length_km` by more than 2 %, or
  `n_down_dip × patch_width_km` from `width_km`;
- patches extend beyond the plane: a patch centre lies closer to an edge than half
  a patch, by more than 1 % of `length_km` or `width_km`. This usually means that
  corner coordinates were given instead of centres. The patch size is
  `patch_length_km` or `patch_width_km`, or else the length or width divided by
  `n_along_strike` or `n_down_dip`;
- `reference_point.along_strike_km` and `down_dip_km` contradict `position`:
  `top_left` must be at 0 / 0 km, `top_center` at L/2 / 0 and `center` at L/2 / W/2,
  within 1 % of the segment length L or width W;
- patch `depth_km` differs from `top_depth_km + down_dip_km · sin(dip)` by more than
  max(0.5 km, 5 %);
- `summary_metrics.max_slip_m` differs from the largest patch slip (> 10 % and > 0.02 m);
- `summary_metrics.mean_slip_m` differs by more than 15 % from both the mean over all
  patches and the mean over non-zero patches;
- `rupture_area_km2` is more than 1.05 × the summed segment area;
- Mw and `seismic_moment_Nm` disagree by more than 0.3 magnitude units, using
  Mw = (log10 M0 − 9.1) / 1.5;
- the record has no `origin_time`, so it is not matched automatically. The build
  also lists it in `event_review.json` (see
  [Automatic event matching](#automatic-event-matching));
- the record has no hypocenter, reference-point or patch coordinates, so the model
  cannot be placed on the map. Its earthquake still has a star if another of its
  models has coordinates (see *Map star* under
  [Fault geometry](#fault-geometry-reference-point-and-patches)).

For a draft, the warnings are only printed, and only once the draft passes the
schema. A missing licence is not a per-model warning: the build prints one `NOTE`
listing the published records without `provenance.license`, and the page shows
"not specified".

## Machine-readable outputs

Besides `index.html`, every build writes:

- `data/models.json`: a JSON array of all published records.
- `data/<id>.json`: one pretty-printed file per published record, where `<id>` is
  the source file name without `.json`.

Both contain the records as they are in `data/models/`, without the browser-only
fields. The only difference is that a missing `model_id` or `event.event_id` is
filled in with the generated value (see [Adding a slip model](#adding-a-slip-model)).
Drafts are not included. Files of records that are no longer published are removed
from `dist/data/`. On the deployed site these files sit next to `index.html`, and
the model panel links to `data/models.json` as *All records (JSON)*.

## Earthquakes and models on the page

The list has one row per earthquake. A row shows the earthquake's name, its
magnitude and the number of slip models. Rows are ordered by origin time, with
undated earthquakes last, and then by name.

- **Name.** An earthquake is named after the shortest `event.name` among its
  published models. That is usually the plainest one. If the selected model's own
  `event.name` is different, the model panel also shows it as *Event name in
  record*.
- **Selecting.** Selecting a row, or the earthquake's star on the map, expands the
  row and selects the earthquake's first model shown. Models are ordered by
  publication year, then citation, then file name. If the selected model already
  belongs to that earthquake, it stays selected. Selecting an expanded row again
  collapses it. Rows and stars also work with the keyboard (Enter or Space).
- **Expanded row.** Each model is listed with its citation, a variant label where
  one is needed, its data types and its phase.
- **Model panel.** The heading is the earthquake's name. For an earthquake with
  several models, a *Published slip model (N)* selector below it lists all of them,
  whatever the filters. Choosing one selects that model and updates the
  [permalink](#permalinks). An earthquake with one model shows *Model:* and the
  citation instead.
- **Variant labels** tell apart the models of one earthquake. The label is the first
  of `model_variant.label`, `name`, `description`, `fault_orientation` and
  `variant_id` that is given. Otherwise it is a "north-dipping" or "south-dipping"
  phrase in `event.name`, else a `model_variant.phase` other than `coseismic`. If
  none applies and several models have the same citation, the file name without
  `.json` is used.
- **Filters** apply to models. An earthquake is listed, and has its star, while at
  least one of its models passes. If filters hide some of its models, its row says,
  for example, "1 of 2 slip models". The page header counts both:
  "*X* of *Y* earthquakes shown · *A* of *B* slip models".
- **Event year** is the year of `event.origin_time`. For a record without an origin
  time, the event-year slider uses the first year from 1800 to 2099 found in
  `event.name`, else in `event.event_id`. That year is used only for filtering and
  is never shown as the event date. A record without any year is never hidden by
  the event-year slider. The publication-year slider uses `reference.year`, and a
  record without one is never hidden by it.

## Permalinks

Selecting a model sets the page address to `#model=<id>`, for example
`index.html#model=Samos2020_Aktug_2021`. Opening such a link, or changing the hash,
selects that model and expands its earthquake in the list.

## Running locally

Requires Python 3.11 or newer. CI uses 3.13.

```bash
python3 -m venv .venv
. .venv/bin/activate              # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
python build.py
python -m pytest
```

Then open `dist/index.html` in a browser. The page loads Leaflet and the map tiles
from the internet. `python build.py` writes `dist/` and updates
`event_registry.json`. When it fails, it leaves both unchanged. It may also write or
delete `event_review.json` (see
[Automatic event matching](#automatic-event-matching)). The tests build
into a temporary directory, never into the repository's `dist/` or registry.

## Continuous integration and deployment

`.github/workflows/deploy.yml` does the following:

- On a pull request: installs `requirements-dev.txt`, runs `python build.py` and then
  `python -m pytest -q`. The build runs first, so a problem in a record is reported
  in the build step with its file and JSON path. Nothing is deployed.
- On a push to `main`, or a manual run on `main`: the same checks, then uploads
  `dist/` (including `dist/data/`) and deploys it to GitHub Pages.

GitHub Pages must be set to deploy from GitHub Actions: *Settings → Pages → Build and
deployment → Source: GitHub Actions*. The workflow never commits anything. If it
warns that `event_registry.json` changed, run `python build.py` locally and commit
the file.

## Licensing and citation

- The licence of each record is given in its `provenance.license`. The page shows
  "not specified" when it is missing, and the build lists such records in a `NOTE`.
- Slip values digitized from published figures or tables are derived from the source
  articles, so the publisher's terms for those articles may apply. Cite the original
  publication of any model you use. The model panel has a ready-made citation and a
  BibTeX entry.
- To cite the database, use Vavlas & Bonatis, *(in prep.)*.
